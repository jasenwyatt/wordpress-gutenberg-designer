# Gutenberg markup rules

WordPress stores blocks using HTML comment delimiters. Generated markup must survive Gutenberg's validation on load — the editor calls each block's `save()` function and compares output to the saved HTML.

## Core block form

```html
<!-- wp:group {"layout":{"type":"constrained"}} -->
<div class="wp-block-group">
  <!-- wp:heading -->
  <h2 class="wp-block-heading">Heading</h2>
  <!-- /wp:heading -->
</div>
<!-- /wp:group -->
```

Core blocks omit the `core/` namespace in serialized comments. Custom blocks include their namespace.

## Dynamic block form

Dynamic blocks may be self-closing:

```html
<!-- wp:latest-posts {"postsToShow":4} /-->
```

## Rules

- Attributes are JSON inside the opening comment.
- Use double quotes in JSON.
- Preserve opening and closing delimiter order.
- Use self-closing syntax **only** for blocks whose saved representation permits it. Most core blocks are containers, not self-closing. See `references/block-validation.md` for the full container/self-closing matrix.
- Match generated HTML classes and structure expected by the selected WordPress version.
- **Do not invent core block attributes.** Only use attributes documented in the target WordPress version's block schemas.
- Avoid manually serialized markup when the correct shape is uncertain; document the uncertainty and verify in WordPress.
- **Never use `core/` prefix inside serialized block comments.** Use `<!-- wp:heading -->`, not `<!-- wp:core/heading -->`.

## Pattern headers

Theme pattern files use a PHP comment header followed by block markup:

```php
<?php
/**
 * Title: Service hero
 * Slug: namespace/service-hero
 * Categories: featured, call-to-action
 * Viewport Width: 1440
 */
?>
<!-- wp:group -->
...
<!-- /wp:group -->
```

Use a unique namespaced slug. Include only metadata justified by the pattern.

## Version-gated attributes

When `minimumWordPressVersion` is supplied, **do not generate attributes introduced in a later version** unless the report explicitly documents the version requirement and the theme polyfills the gap.

Key version gates (see `references/block-validation.md` for the full matrix):

| Attribute / feature | Minimum WP | Fallback when targeting earlier |
| --- | --- | --- |
| `theme.json` version 3 | 6.6 | Use version 2 for 6.1–6.5 |
| `aspectRatio` on `core/image` | 6.5 | Scoped CSS `aspect-ratio` |
| `scale` on `core/image` | 6.5 | Object-fit in scoped CSS |
| `layout.type: "grid"` on `core/group` | 6.6 | `core/columns` or scoped CSS grid |
| `dimensions.minHeight` | 6.3 | Inline style or scoped CSS |
| `typography.textWrap` | 6.6 | Omit; browser handles wrapping |
| `shadow` presets | 6.6 | Scoped CSS `box-shadow` |
| `border.radius` object form | 6.3 | String form `"1.25rem"` |
| `spacing.blockGap` object form | 6.4 | String form `"2rem"` |

The validator (`scripts/validate-output.mjs`) flags version-incompatible attributes when the target version is known.

## Common markup traps

### 1. Both preset class and inline style for the same property

Bad — will trigger validation mismatch:
```html
<!-- wp:heading {"fontSize":"display"} -->
<h2 class="wp-block-heading has-display-font-size" style="font-size:clamp(2.75rem,6vw,5.5rem)">...</h2>
<!-- /wp:heading -->
```

Good:
```html
<!-- wp:heading {"fontSize":"display"} -->
<h2 class="wp-block-heading has-display-font-size">...</h2>
<!-- /wp:heading -->
```

The `has-*-font-size` class is generated by the `fontSize` attribute. Adding an inline `style.fontSize` duplicates the value and may cause `save()` output to differ.

### 2. Container blocks written as self-closing

Bad:
```html
<!-- wp:group {"align":"full"} /-->
```

Good:
```html
<!-- wp:group {"align":"full"} -->
<div class="wp-block-group alignfull">...</div>
<!-- /wp:group -->
```

### 3. `core/` namespace in serialized comments

Bad:
```html
<!-- wp:core/heading {"level":2} -->
```

Good:
```html
<!-- wp:heading {"level":2} -->
```

### 4. Attribute type mismatches

- `level` on `core/heading` is **integer** `1`–`6`, not string `"1"`.
- `dropCap` on `core/paragraph` is **boolean** `true`/`false`, not string `"true"`.
- `dimRatio` on `core/cover` is **integer** `0`–`100`.
- `postsToShow` on `core/latest-posts` is **integer**.
- `openInNewTab` on `core/social-link` is **boolean**.

### 5. Conflicting style structures

`blockGap` accepts:
- String (6.1+): `"blockGap": "var:preset|spacing|40"`
- Object with `top`/`left` (6.4+): `"blockGap": {"top":"var:preset|spacing|40","left":"var:preset|spacing|40"}`

Do not use object with only `left` or only `top` — it is invalid in all versions.

## Preset usage

Prefer WordPress preset syntax in style values:

```text
var:preset|color|brand
var:preset|spacing|60
var:preset|font-size|display
var:preset|shadow|soft
```

Use the corresponding generated CSS variables only in standalone CSS:

```css
var(--wp--preset--color--brand)
var(--wp--preset--spacing--60)
```

## What should remain CSS

Use scoped CSS for features not cleanly represented by `theme.json`, including:

- pseudo-elements,
- complex selectors,
- advanced responsive grid behavior,
- nontrivial animations,
- progressive enhancement states,
- highly specific component relationships.

Do not duplicate global token definitions in CSS.
